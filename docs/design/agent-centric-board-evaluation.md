# 以智能体为单位的任务看板 · 整体评估

> 对应设计：[agent-centric-board.md](./agent-centric-board.md)
> 评估时间：2026-11-21　范围：设计文档 §7 改动清单的全部落地项
> 结论：**方案要求的改动已全部落地并验证；有 4 处与原始方案的偏差和 3 项未验证，逐条列在 §3、§4。**
> 建议先看 §5「需要你拍板的调整」，其余是取证。

## 1. 一句话结论

看板的最小单位已经从「一张任务」变成「一张任务 × 一个智能体」：智能体有了五段式定义、
成为一级入口，卡片上的 `assignee` 真正决定派给谁，人可以直接按智能体派活；
工作室与调度器提议也接上了。**这不是功能拼盘的加法，而是归属这一维被接进了调度链路。**

## 3. 与方案的偏差（4 处，均已写入设计文档）

1. **工作室对话不持久化**：方案原写「对话存 sqlite turns」，实现改为存在本次界面会话里。
   理由：草稿未发布，重开即废；为一个一次性编辑器加一张表和一套清理策略，成本大于收益。
   **代价**：关掉窗口再打开要继续改，只能重新说一遍。
2. **工作室入口在智能体视图顶部**，不在编辑器弹窗里再叠一层弹窗。
3. **新建智能体自动进入允许名单**：前端不再拼 id（保存前还不存在），由后端补录。
4. **id 允许中日韩字符**：原校验只允许 ASCII，改成「字母数字 + `-_`」，这样
   `assignee: [文档写手]` 是人也能读、能写的记号。

## 4. 未验证与风险

1. **没有真机界面走查**：只跑了 jsdom 组件测试，没有构建桌面 App 看真实排版
   （行视图在窄窗口下的换行、密集行的滚动高度都没看过）。
2. **没有真实 CLI 的端到端派发**：`router_assign_task` 的派发路径与手动「开始」共用同一函数，
   但「指派并开工 → zellij 里真的跑起来」这一步没有在本机实跑。
3. **全量 `cargo test --lib` 仍有约 20 个 `proxy::*` / `gateway::*` / `mode::*` 网络类用例失败**
   （`ForwardFailed` → 502、上游目录发现失败），单条运行同样失败，不是并发抖动。本轮改动没有触及
   这些模块，但未能机械证明改动前是否同样失败——干净的 HEAD worktree 在本机无法编译
   （缺 `ghostty-sdk` / `binaries` / `sidecar/dist` 生成物）。
4. **判官仍会为「有人工归属」的卡消耗一次判断**：归属只在结算层覆盖。省下这次调用的优化没做，
   因为要先改 episode 的输入结构，收益不确定。

## 5. 需要你拍板的调整（6 条）

1. **未注册归属的出口**：现在卡片会标「未注册」，手动「开始」直接报错（不退回默认）。
   要不要在详情页给一个「清除归属」一键？现在要先在下拉里选回「未指派」。
2. **行内 Done 留几张**：现在固定 3 张。不同节奏的团队可能要 0 或 5，要不要做成设置项？
3. **工作室对话是否落库**：如果希望关掉窗口后还能接着改，就得加表；否则维持现状。
4. **智能体定义是否拆独立表**：现在是 `router_settings` 一行 JSON。改名/删除已经不影响引用，
   但定义变多、五段式变长之后，这一行会越来越长，读写都是整份。
5. **「未参与派发」的智能体行是否默认隐藏**：现在全显示 + 徽标。人多了会成为噪音。
6. **提议的判据**：现在是「同标签 + 14 天 + 3 张」。要不要把「同一应用被人工派了几次」也当信号？
   现在的判据在标签缺失时会落到「未分类」，那条建议通常没什么用。
