## 一、产品概述

phi 是一个运行在本机的 **AI Agent 网关与资源编排平台**。它以常驻本地网关为核心：向上兼容主流 Agent（Claude Code、Codex、Gemini CLI、OpenCode 等），向下连接多个模型供应商与账号，在中间完成**协议转换、智能路由、配置管理、成本核算**四件事。

用户只需把 Agent 的接入地址指向 phi，即可获得：

| 能力 | 说明 |
|---|---|
| **统一入口** | 一个本地地址接入所有 Agent；模型与供应商在网关侧切换，Agent 无感知 |
| **智能路由** | 按任务意图、上下文、价格与历史质量自动选择模型，且每次路由给出可解释的依据 |
| **配置管理** | 一个界面管理多个 Agent 的配置、环境变量、MCP、Skills 与 Prompt，支持版本与回滚 |
| **成本账本** | 请求级 Token 与费用记录，按项目、仓库、Agent 归因，支持预算告警与硬限流 |
| **故障恢复** | 供应商异常自动降级；配置可一键还原；Agent 不因网关故障而断粮 |

phi 不做模型训练，不做云托管推理，也不经营账号转售。它的价值来自**把用户已有的模型资源组织得更好**。

## 二、背景与问题

### 2.1 行业背景

AI 编程已进入"多 Agent、多模型、多账号"的常态：一个开发者可能同时用 Claude Code 写代码、Codex 做重构、Gemini CLI 查资料，背后对应不同的供应商、订阅和 API Key。同时，模型的价格、上下文长度和能力差异巨大且更新极快，任务与资源的匹配越来越复杂——这已经超出手工管理配置文件的能力边界。

### 2.2 用户的四个真实问题

1. **配置碎片化**：每个 Agent 的配置格式、环境变量和生效路径都不同；切换模型等于手工改文件，易错、难回退。
2. **资源不透明**：手握多个订阅与 API Key，却不知道哪个模型适合当前任务、哪个账号还有额度，资源大量闲置。
3. **故障难恢复**：供应商限流、额度耗尽或服务异常时，工作流直接中断，只能手动排查换源。
4. **成本不可见**：没有人能准确回答"这个项目这个月花了多少钱、花在哪类任务上"。

### 2.3 现有方案的空白

| 方案类型 | 代表 | 解决了什么 | 没解决什么 |
|---|---|---|---|
| 配置切换器 | cc-switch 等 | 快速切换默认模型配置 | 无常驻网关、无智能路由、无成本闭环、生态管理弱 |
| 通用云网关 | OpenRouter 等 | 多供应商聚合、统一 API | 不理解本地 Agent 工作流，数据出域，无法管理本地配置 |
| 本地订阅复用网关 | magpie 等 | 协议互转、订阅复用、故障转移 | 成本核算浅、会话观测弱、无跨设备同步 |

**phi 的机会**：用本地网关的架构承载"配置管理 + 智能路由 + 成本闭环"的完整体验，同时保证数据留在用户本机。

## 三、产品理念

### 愿景

让 AI Agent 像使用操作系统资源一样使用模型资源：入口统一，策略透明，资源可替换，成本可解释，数据掌握在用户手中。

### 使命

降低 AI 编程工具的配置复杂度和使用成本，让个人开发者与小团队能够安全地组合多个 Agent、模型和账号，持续获得更高的任务完成效率。

### 设计原则

1. **本地优先**：请求、账本和凭据默认留在本机；云端能力可选。
2. **供应商可替换**：用户的 Agent 配置不绑定单一模型或平台。
3. **策略可解释**：每次路由都能说明选择了什么、为什么选择、消耗了什么。
4. **失败可恢复**：供应商异常时自动降级，网关故障时允许快速恢复原生配置。
5. **渐进式自动化**：先提供可控的规则，再提供智能建议，最后才允许自动决策。
6. **合规优先**：只管理用户有权使用的账号、密钥和模型资源，不把规避限制作为卖点。

## 四、产品架构：六层闭环

phi 的产品能力分为六层，各层职责与用户价值如下：

| 层 | 产品职责 | 用户获得的价值 |
|---|---|---|
| 协议接入层 | 兼容 Anthropic、OpenAI、Gemini 等协议，统一流式输出、工具调用、视觉和推理字段 | Agent 可以接入不同模型和供应商 |
| 网关运行层 | 本地代理、鉴权、请求转发、协议转换、重试、熔断、缓存和离线状态管理 | 使用稳定，切换成本低 |
| 决策路由层 | 根据任务意图、上下文长度、工具调用、延迟、价格、额度和历史质量选择模型 | 自动获得质量、速度或成本的平衡 |
| Agent 配置层 | 管理各 Agent 工具的配置、环境变量、MCP、Skills 和 Prompt | 一套环境配置多种工具，可恢复、同步和复用 |
| 资源与账本层 | 记录请求、Token、价格、额度、项目、会话、模型质量和失败原因 | 知道钱花在哪里，并能据此优化 |
| 策略与协作层 | 预算、权限、团队策略、审计、配置版本和共享 | 从个人工具升级为团队基础设施 |

最有价值的不是某一层单独存在，而是六层形成的**核心闭环**：

```
请求进入 → 识别任务 → 选择资源 → 执行与降级 → 记录成本和质量 → 反哺下一次路由
```

单点功能可以被模仿，闭环数据会随使用时间复利增长——这是 phi 长期壁垒的来源。

### Token 账本：从统计页面到决策数据层

账本不是用量展示页，而是驱动路由与商业决策的数据层，至少包含：

- 请求级输入、输出、缓存 Token 与费用估算；
- 按项目、仓库、Agent、成员、会话和模型归因；
- 供应商额度、重置时间和剩余额度；
- 延迟、错误率、重试次数、上下文超限和工具调用成功率；
- 预算告警、硬限流和审批策略；
- 任务完成质量或用户反馈，用于评估路由是否有效。

## 五、核心功能模块

### 5.1 桌面客户端与 CLI

- 菜单栏常驻应用，可视化配置、模型目录、路由策略和账本；
- CLI 支持脚本化安装、切换、诊断和导出；
- 一键启停网关，一键恢复 Agent 原生配置；
- Windows、macOS、Linux 分阶段支持。

### 5.2 本地协议网关

首期支持：

- Anthropic Messages、OpenAI Chat Completions、OpenAI Responses、Gemini Generative Language 四种协议；
- 流式响应、工具调用、图片、推理内容和上下文错误的统一处理；
- 本地鉴权和请求 ID；
- 超时、重试、熔断与供应商健康检查；
- 可选的本地缓存，明确标注缓存命中和数据边界。

**安全默认值**：只监听回环地址、随机本地令牌、凭据进入系统 Keychain、敏感日志脱敏、远程访问显式开启。

### 5.3 智能路由引擎

路由策略按复杂度分层，可独立启用：

| 策略 | 规则 |
|---|---|
| 固定路由 | 项目或 Agent 固定使用指定模型 |
| 规则路由 | 按任务标签、模型能力、上下文、图片和工具调用选择 |
| 故障转移 | 按错误类型切换供应商 |
| 成本路由 | 在质量约束下优先低成本模型 |
| 质量路由 | 在预算约束下优先历史成功率高的模型 |
| 意图路由 | 识别编码、规划、审查、总结和简单问答等任务类型 |
| 学习型路由 | 基于历史延迟、成本和反馈提出策略建议，默认需用户确认 |

路由结果必须可解释，例如：

> 选择 Model A：任务属于代码审查，需要长上下文；当前项目剩余额度充足；Model B 最近错误率较高。

### 5.4 Agent 配置管理器

区别于通用模型网关的核心产品面：

- 管理多个 Agent 的配置文件和环境变量；
- 只修改必要字段，保留注释、顺序和用户格式；
- 支持 Profile，如"低成本开发""高质量审查""离线本地模型"；
- 管理 MCP、Skills、Prompt 和项目级指令；
- 记录配置版本、差异和回滚点；
- 支持 Git 导出、加密备份和跨设备同步；
- 提供配置诊断，发现冲突、失效路径和过期模型。

### 5.5 Token 账本与控制台

账本分三层：

- **事实层**：记录每次请求的 Token、耗时、状态码、模型、供应商和项目；
- **核算层**：按价格表和供应商账单估算成本，允许用户修正价格；
- **决策层**：生成预算、路由建议、额度计划和异常告警。

所有价格估算均标注"估算"或"已对账"，不把第三方返回的 Token 数量包装成绝对准确的财务数据。

## 六、产品特点与差异化

### 6.1 五大产品特点

1. **本地优先，数据自主**——请求、账本、凭据默认不出本机；代码上下文不经过第三方托管平台。
2. **一站式 AI 编程资源控制台**——模型、账号、Agent、项目、预算收进同一个控制平面，取代散落在各处的配置文件与后台页面。
3. **可解释的任务感知路由**——理解编码、重构、审查、规划等任务差异，自动匹配模型，并展示每次选择的理由。
4. **成本—质量反馈闭环**——能回答"哪个模型在这个仓库的审查任务上更可靠、平均慢多少、贵多少"，数据随使用持续复利。
5. **外科手术式配置，永远可回退**——只改必要字段、保留用户格式，一键还原原生配置，Agent 不被 phi 锁定。

### 6.2 三大差异化战略

**差异化一：AI 编程资源控制台。** 竞争对象不是某个单一的配置切换器，而是用户手上的配置文件、多个供应商后台、各种用量统计和手工排障流程。phi 把它们整合为一个控制平面。

**差异化二：可解释的任务感知路由。** 多供应商聚合是基础能力，不构成壁垒。真正的差异是理解 AI 编程任务——代码补全、重构、调试、规划、审查、文档和测试使用不同的模型组合，并向用户展示路由依据。

**差异化三：成本与质量的反馈闭环。** 只转发请求的产品容易被通用网关替代；能基于历史数据持续改善路由决策的产品，会随时间形成数据与策略壁垒。

### 6.3 竞争位势小结

- 对**配置切换器**：架构代差——从"改配置"升级为"常驻网关 + 决策闭环"；
- 对**通用云网关**：场景与信任差异——本地优先、理解 Agent 工作流、代码不出域；
- 对**同类本地网关**：完成度差异——成本账本、生态管理（MCP/Skills/Prompt）与跨设备同步补齐短板。

## 七、技术选型与实现策略

### 7.1 桌面端：Tauri + Rust

Tauri + Rust 适合桌面客户端：体积小、内存占用低、系统集成好、安全边界清晰。但需要清醒认识其边界：

1. AI 请求的主要耗时来自网络和模型推理，壳层性能只影响启动、配置操作和本地 UI 响应；
2. 网关的核心指标是协议兼容性、流式稳定性、故障恢复、数据正确性和可观测性，而非极限性能；
3. Rust 提高开发门槛，在协议与供应商快速变化期，开发速度和可维护性可能比极限性能更重要。

### 7.2 控制台设计与实施顺序

控制台采用「供应商资源 → 路由策略 → Agent 接入 → 请求观测」的组织方式。供应商回答“有哪些资源”，路由回答“请求怎么选择资源”，Agent 页面回答“工具如何接入”。三者不能继续混在单个应用的供应商卡片中。

#### 导航与页面职责

- **供应商**：全局目录，集中查看各应用保存的供应商配置。首批按应用分组，进入对应应用管理凭据、模型和配置；名称相同的配置不自动合并。
- **路由**：全局总览，展示支持本地网关的应用、直连 / 路由 / Stack 模式、配置目标以及实际接入状态；进入应用配置具体策略。网关停止、未接入和读取失败必须分别显示。
- **Agent 接入**：保留当前应用入口、专属配置和原有模式操作。Claude Desktop 的模型映射、共存式客户端配置不冒充通用网关路由能力。
- **用量与请求观测**：沿用用量统计，后续补充请求决策轨迹，与路由编辑双向跳转。

视觉沿用现有桌面控制台：紧凑侧栏、稳定页头、表格与分组列表、语义化状态颜色。展示事实优先；没有数据时显示未知或读取失败，不填入示例健康度、成本或请求数。

#### 数据模型演进

目标模型分为 Supplier（供应商）、Credential（凭据引用）、Endpoint（协议与地址）、Model（上游模型）、RoutePolicy（选择与降级策略）、AgentBinding（工具接入）和 RequestTrace（一次请求的选择与执行记录）。凭据不进入目录展示或路由解释。

现有 `Provider` 仍是按应用保存的配置，不等同于独立的全局 Supplier；现有 `UniversalProvider` 通过同步生成应用配置，也不等同于运行时共享资源池。首批只建立统一读取视图，使用 `(appId, providerId)` 标识记录。后续数据库迁移必须显式保留应用绑定和原始配置，提供备份、冲突预览与回退，不能按名称或地址静默去重。

路由策略后续独立保存匹配条件、候选资源、优先级、回退规则与启用状态；先完成固定路由和故障转移，再加入模型别名、能力规则和意图路由。参考 magpie 的供应商分组、路由配置和请求轨迹分工，不直接移植其账号、协议或运行时假设。

#### 分批交付与验收

| 批次 | 交付 | 验收边界 |
|---|---|---|
| A：控制台入口 | 全局供应商目录、路由总览、导航持久化、应用管理跳转 | 使用现有真实接口；支持加载、空列表、局部失败、重试；旧导航与应用操作兼容 |
| B：资源独立化 | Supplier / Credential / Endpoint / Model 存储与编辑、显式迁移 | 同名记录不误合并；应用配置可回退；凭据不泄漏 |
| C：策略独立化 | 路由策略编辑、模型映射、候选优先级与故障转移 | 配置经过校验并实际作用于请求；能解释选择和降级原因 |
| D：观测闭环 | 请求轨迹、错误归因、成本估算与策略跳转 | 请求事实与当前配置分开；估算明确标注；敏感信息脱敏 |

截至 2026-10-13，控制台已接通 B—D 的基础流程：

- 供应商页使用独立资源池，新建复用原有完整添加页的模板搜索、分类与配置表单，支持切换 Claude / Codex / Gemini / Grok 模板库；通用模板按所选协议一次性保存多个出口，不写入或同步客户端配置。支持编辑、删除、导入预览、按协议筛选和搜索；模型发现使用后端已保存的凭证，返回列表供选择并合并，保存前不会修改现有模型。策略引用可直接跳转。
- 路由页支持精确模型别名、默认策略、优先级、启停、候选排序与故障转移；预览使用与运行时一致的匹配顺序，不发送上游请求。空候选策略只能保持停用，Gemini 仅接受 Gemini 原生协议。
- Agent 可从路由页直接接入资源池，无需先建立应用供应商副本；未命中策略时拒绝请求。原有应用路由的默认目标单独展示；显式选择的 Stack 模型继续使用原有绑定。退出或停止网关会恢复直连配置；没有应用供应商记录时，恢复投影保存于设备本地的 `live-state.json`（0600、不参与同步）。
- 请求轨迹保存请求模型、目录版本、策略与供应商名称快照、各次尝试的固定错误类别，以及最终完成、失败或中断状态。用量来自响应；缺失数据或定价显示未知，费用标为最终响应的 USD 估算，不宣称包含失败尝试的完整账单。策略与请求记录可以相互跳转，删除策略不影响已有快照。开启请求日志后记录，目录中不包含密钥或响应正文。

入口仅允许回环监听，除健康检查外须通过每个应用独立的本地令牌认证，认证在读取请求体之前完成。令牌随 PHI 进程轮换，接入和启动恢复时更新原生配置；缓存配置的客户端需要重启。官方 Codex 登录与本地认证分别通过 `Authorization` 和 `x-phi-token` 传递；官方代理要求开启统一会话历史以使用支持独立头的 custom 路由，未开启时保留直连并拒绝进入代理。

本轮不包含能力/意图路由、预算控制、逐尝试成本账本及供应商凭证迁入系统 Keychain。供应商密钥仍在独立本地 SQLite 表中；这不等同于后续凭据保险库。

### 7.3 工程原则

- 核心网关设计为**独立进程**，便于 CLI、桌面端、Docker 和团队版复用；
- 数据面使用 SQLite，敏感凭据交给系统 Keychain；
- 高吞吐场景按基准测试结果将关键路径 Rust 化，不预设"Rust = 卖点"；
- 遵守 5.2 节安全默认值，安全能力先于功能扩展。

## 八、目标用户与核心场景

### 8.1 首发用户：重度 AI 开发者

同时使用 Claude Code、Codex、Gemini CLI、OpenCode 等工具，拥有多个供应商，经常手动改配置、切换模型、处理额度与故障。

痛点：配置格式不统一、模型能力与价格不透明、额度与故障需手动排查、项目成本不可见、订阅与 API 资源闲置。

### 8.2 增长用户：小型 AI 原生团队

需要共享配置和路由策略，但不希望把全部代码请求发送到第三方托管平台。

需求：成员权限与项目预算、统一供应商管理、请求审计与成本归因、配置版本化、私有部署与数据隔离。

### 8.3 远期用户：模型服务商与硬件节点运营者

通过标准协议接入自己的模型、GPU 或推理服务，获得稳定的开发者流量。该方向必须建立在明确的授权与商业合同之上。

### 8.4 典型场景

- **场景一（无感容灾）**：主力供应商额度耗尽，phi 按故障转移策略切换到备用账号，会话不中断，事后在账本中看到切换记录与成本差异。
- **场景二（成本归因）**：月底复盘，按仓库查看本月各任务类型的 Token 消耗与费用，发现审查任务占了 40% 成本，随即调整该项目路由策略。
- **场景三（快速接入）**：新装一个 Agent，五分钟内通过 phi 的配置模板完成接入，历史配置已自动备份。
- **场景四（团队策略，远期）**：团队设定"生产仓库只允许指定模型 + 月度预算上限"，新成员加入即继承策略。

## 九、产品路线图（0—18 个月）

### 阶段一（0—3 个月）：个人开发者可用

**目标**：证明核心链路，不追求一次覆盖所有 Agent。

- macOS、Windows 优先；Tauri + Rust 桌面壳层，网关进程可独立运行；
- 支持 Anthropic、OpenAI 两种协议与 6—8 个主流 Agent；
- 自定义 API Key 与 OpenRouter 等聚合供应商；
- 固定路由、规则路由、故障转移；
- 配置 Profile、原子写入和一键恢复；
- 请求日志、Token 账本、基础价格表；
- 回环监听、Keychain、脱敏日志和诊断命令。

**成功标准**：新用户 10 分钟内完成首次请求；常见 Agent 配置切换成功率超过 99%；流式请求与工具调用在主流场景稳定；用户能清楚看到一次请求的模型、成本和失败原因。

### 阶段二（4—9 个月）：形成产品差异

- Gemini 协议与更多 Agent 支持；
- 意图路由与能力路由；
- 项目、会话、仓库维度的成本归因；
- 预算告警和硬限流；
- 模型能力目录与健康评分；
- MCP、Skills、Prompt 的统一管理；
- 加密备份、Git 配置导出和跨设备同步；
- 基于历史数据的路由建议；
- Web 控制台与 CLI 完整化。

### 阶段三（10—18 个月）：团队与商业化

- 团队工作区和成员权限；
- 团队级供应商密钥管理；
- 项目预算、审计和成本分摊；
- 私有部署、SSO、组织策略和合规日志；
- 可插拔的本地模型与 GPU 节点；
- 与明确允许代理或转售的模型服务商合作；
- 托管协作网络的封闭测试。

## 十、商业模式

### 10.1 版本与定价

| 版本 | 定价 | 核心能力 |
|---|---|---|
| 免费个人版 | 0 元 | 本地网关、基础协议转换、少量 Agent 配置、本地账本、固定路由与基础故障转移 |
| Pro 订阅 | 8—15 美元/月（按地区等价） | 高级意图路由、多设备同步、高级成本分析、自定义策略与价格表、配置版本/备份/恢复、高级诊断、本地与云模型混合编排 |
| Team 订阅 | 49—199 美元/月起（按席位或组织） | 团队供应商池、成员权限、项目预算、用量与成本分摊、组织级路由策略、审计日志、SSO 与私有部署支持 |

收费对象是**软件能力**，不包含模型调用费用。

### 10.2 服务商与生态收入

后期与模型供应商、云 GPU、企业部署服务商合作，获得集成费或渠道分成。必须明确披露推荐关系，不允许商业利益暗中改变用户的路由结果。

### 10.3 资源网络收入（远期）

资源网络是远期方向，仅在授权、隔离、结算和责任体系成熟后探索，按三个稳妥路径推进：

1. **团队资源池**：组织自有的 API Key、企业账号或自部署模型，按成员和项目分配额度；
2. **自托管边缘节点**：用户把自有 GPU、本地模型或已授权供应商接入网络，默认只服务自己或明确授权的团队；
3. **合规算力市场**：只接入明确允许转售、代理或共享的供应商，采用隔离租户、审计、结算和撤销机制。

早期产品不依赖资源网络即可成立，优先把"统一入口、智能决策、成本闭环"做成刚需。

## 十二、风险与应对

| 风险 | 应对 |
|---|---|
| 供应商条款与账号风险 | 只接入用户有权使用的 API Key、企业账号和明确授权的服务；不以共享订阅、规避地区限制或绕过官方客户端限制为卖点 |
| 凭据与隐私风险 | 凭据进 Keychain；日志默认脱敏；默认仅监听 127.0.0.1；远程访问显式开启并强鉴权；账本可关闭内容记录只留元数据 |
| 网关单点风险 | 守护进程独立运行、健康检查、一键恢复原生配置、配置备份、紧急旁路模式；Agent 不永久依赖桌面 UI |
| 模型质量不可控 | 保留固定策略与手动覆盖；智能路由可解释、可关闭，并展示失败后的实际降级路径 |

## 十三、品牌命名

### 正式品牌名：phi（斐）

产品正式命名为 **phi（斐）**，官网为 **[phi.semibot.ai](https://phi.semibot.ai)**。

命名理由：

- **φ 是黄金比例**：路由引擎的核心命题正是"成本与质量的最优平衡"——在预算约束下追求质量、在质量约束下控制成本，φ 恰好是这个平衡点的象征；
- **φ 是收敛常数**：呼应"请求进入 → 决策 → 记录 → 反哺优化"的收敛闭环，每一次路由都让下一次更优；
- **"斐"取自"斐然成章"**：形容成果卓著、文采斐然，与 AI 生成代码与内容的产品气质契合；读音与 phi 一致，中英品牌天然统一；
- **极简、易记、易注册**：三个字母，适合作为 CLI 命令（`phi`）、桌面应用名和生态命名空间，记忆与传播成本极低。

英文品牌直接使用小写 **phi**，产品全名可用 **phi — AI Agent Gateway**。phi.semibot.ai 作为起步官网，借助 semibot.ai 的既有信任度完成冷启动；产品独立化后可再评估 phi.ai、phi.dev 等独立域名。

### 上线前命名核查

- **商标**：核查目标市场（软件、SaaS 类别）中 phi 的可注册性与在先权利；
- **包名**：核查 npm、PyPI、crates.io、Homebrew 等仓库中 `phi` 的占用情况，必要时准备 `phigw` 等命令别名；
- **同名项目**：排查同名开源项目与商业产品，避免混淆；
- **语境歧义**：文档与文案中避免与"受保护健康信息（PHI）"缩写场景重叠，防止检索与语义混淆。

## 十四、结语：战略定位

phi 真正要做的，不是把多个模型装进一个桌面窗口，也不是单纯追求 Rust 的性能，而是建立一个**用户可控制的 AI Agent 资源控制平面**：连接不同协议和工具，按任务选择资源，记录真实成本与质量，并让这些数据持续改善下一次决策。

战略收敛为一句话：

> **phi 是一个本地优先、可解释、可观测的 AI Agent 网关，让个人和团队用统一策略管理模型、账号、配置与成本。**

节奏上：早期用 Pro 和 Team 订阅验证商业闭环；中期用成本与质量数据、Agent 配置生态和团队策略形成壁垒；远期在明确授权和合规隔离的前提下，探索企业私有资源池与模型节点网络。
