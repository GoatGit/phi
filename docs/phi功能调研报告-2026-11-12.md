# PHI 功能调研报告

**副题：从 magpie 源码实测出发，找 PHI 真正能赢的那一格**

- 日期：2026-11-12
- 调研对象：PHI（GoatGit/phi）、magpie（yetone/magpie）
- 证据基础：两个项目的公开仓库与文档；magpie 源码本地克隆（HEAD `c75a1a0f8`，2026-11-12）；PHI 未本地克隆，仅依据其 README 与文档索引
- 性质说明：**本文是竞品与技术可行性分析，不是已实现方案**。所有"建议""估工""判定规则"均为设计口径，未经代码验证。

---

## 一页结论

1. **正面战场打不过。** magpie 在 agent 覆盖（40+）、模型覆盖（20+）、切换便捷度、跨平台、插件生态、每日迭代速度上全面领先。任何"我们也做网关、也做路由、也做插件"的打法都是送死。
2. **它的护城河是"琐碎正确性"的工业化。** 7 周 7,668 次提交、3,800 个 tag、123 万行 Go（含测试）、94 个内部包、17 篇子系统文档；每晚由 AI 复盘当日提交并把教训沉淀成规则。以迭代速度或工程细腻度竞争，必输。
3. **它有一条明确且自觉的边界：只读，不执行。** `internal/sessions` 包首行注释原文："It only ever reads the agents' folders." 它读会话、算成本、算 token，但从不跑用户的命令，也不碰用户的仓库。
4. **因此 PHI 唯一的结构性机会，是"执行现场"。** 三个候选：接棒（会话级续跑）、成绩单（结果账本）、编排接力（多 agent 分工）。
5. **主推「成绩单」，配「接棒」当钩子。** 成绩单的问法正好与 magpie 的 `tune` 形成对偶：它问"改参数能省多少 token"，PHI 问"换模型会返工多少次"。
6. **但成绩单不能一步到位。** 只有会话数据时，今天只能算出**可靠性榜**（谁更少翻车），算不出**质量榜**（谁更管用）。质量榜需要额外三件东西：模型归因表、任务切分、跨时间的返工观察。
7. **窗口很窄。** 目标仓库每天新增上百次提交，今天没有的字段，下周可能出现。若要做，就要快。
8. **「编排接力」不必自研载体。** Backlog.md（MIT、Markdown 原生看板、明确为 agent 设计）与本方案的结构化交接单几乎 1:1 对齐。正确分工是让**它管"该做什么、做到哪一步"，PHI 管"到底做成了没有"**。详见第十节。
9. **但最快能落地的是一个更小的东西：教训库。** 它只吃会话数据、不等 72 小时观察窗，工程量最小、当天就能被用户感知。建议把它当"入场理由"，把成绩单当"护城河"——先让人愿意住进来，再让他搬不走。详见第十一节。
10. **但源码核对把入场顺序又推翻了一次。** 教训库的注入通道（`AGENTS.md` / `SKILL.md`）与 PTY 托管，在本仓库都已成立；“在等我”只差一个探针；同时成绩单与教训库在第 0 天都是空的。因此更可能的顺序是 **G0 探针 → 候诊室 → 教训库 → 成绩单**。成绩单仍是护城河，但未必是第一个上桌的菜。详见第十三节。

## 二、两个项目的事实底座

### 2.1 PHI

- 定位：**桌面工作台**，Tauri 2 + Rust + React，MIT
- 形态：应用内直接跑 CLI（macOS 内置原生 Ghostty 终端，其他平台取决于系统集成）
- 管理对象：Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、ZCode 等
- 本地网关：协议转换、模型聚合、**故障转移与熔断**
- 统一管理 MCP、Skills、提示词；按工具支持的方式同步
- 会话与用量：浏览会话、Token、费用估算、缓存命中、趋势
- 数据本地优先，默认存 `~/.phi/`；订阅引擎为 Go 侧车
- 界面四语：简中 / 繁中 / 英 / 日

- 定位：**菜单栏 + 本地网关**（`127.0.0.1:3425`），MIT

- 覆盖：40+ agent、20+ 模型；`group/` 路由组在额度耗尽时自动换下一个账号
- 生态：插件市场（`magpie-community/plugins`）、Discord、Kimi 等赞助

## 四、它的结构性盲区

源码里有一条非常干净的边界。`internal/sessions/sessions.go` 首行注释：

> It only ever **reads** the agents' folders.

由此推出三个缺口：

1. **不执行。** 从不跑用户项目里的命令，因此拿不到"用户自己的验收结果"。它只能看 agent 自述的工具结果。
2. **不碰工作区。** 不知道 git 里发生了什么：改动有没有被回滚、有没有被人重写。
3. **没有"任务"这个对象。** `internal/usage` 里没有 Task（检索无结果），只有 request / account / model / session。它知道每一次调用花了多少钱，不知道这一次活儿有没有干成。

**所以缺的那一格是：magpie 有一条完整的成本曲线，没有一条质量曲线。**

## 五、三个候选功能

### 5.1 候选 A：接棒（Session Baton）

**是什么**：额度耗尽、上下文超限、供应商故障、进程崩溃时，在同一任务内自动换账号/换模型续跑，并注入交接单（已改文件、已验证结论、卡住的那一步、剩余待办）。

**修正后的判断**（重要）：
- 早前认为"啃会话格式"是它的技术门槛，**这一条不成立**——magpie 已经能读写并搬移 Claude 会话、修补 Codex 的 provider stub 让 `codex resume` 可用。
- 真正的门槛是**监督运行中的进程**：只有托管 PTY 的人才知道 agent 是"跑完了"还是"刚死"。
- 因此接棒 = 检测 + 重启 + 交接单 + 验收；后两件其实就是候选 B。

**评级**：★★★★☆（钩子价值高，用户一句话就懂："我跑到 80% 挂了"）

### 5.2 候选 B：成绩单（结果账本）—— 主推

**是什么**：给每个模型在**用户自己的代码库**上记成绩：一次通过率、返工次数、被回滚次数、单任务成本。不是 benchmark，是用户自己的血。

**为什么对偶得漂亮**：magpie 的 `tune` 问"如果我改参数，能省多少 token"；成绩单问"如果我换模型，会返工多少次"。**一个优化输入价格，一个拥有输出质量。**

**为什么它抄不动**：不是数据不可得（它也能读 `is_error` 和 `exit_code`），而是**位置**——它不跑用户的命令、不碰工作区，也就没有资格下判决。

**评级**：★★★★★（护城河：数据攒三个月即形成迁移成本）

### 5.3 候选 C：编排接力（多 agent 分工）

Claude Code 出方案 → Codex 写实现 → 便宜模型复查。magpie 只做"路由到模型"，架构上不做"agent 与 agent 之间的工序编排"。

**评级**：★★★☆☆（最好的融资故事，最不该现在做的东西）

### 5.4 备选 D：寄生打法

magpie 把 plugin tools 开放成 MCP server 给所有 agent 用。PHI 可以反过来**做成 magpie 的插件**，从它的开放面进入、拿数据，而不是正面建网关。

**评级**：★★★☆☆（战术选项，不是战略）

### 5.5 排序结论

- **矛**：成绩单（候选 B）
- **矛的把手**：接棒（候选 A）
- **留给下一轮叙事**：编排接力（候选 C）
- **品牌口径**：「magpie 让每个 agent 都用上最好的模型；PHI 告诉你——哪个模型真的把你的活干成了。」

## 六、核心难题：PHI 怎么知道任务完成还是返工？

### 6.1 总原则

**不要去问 agent"做完了没"，要看世界接受了没有。** agent 自述"已完成"是最不可靠的信号。

三个相互独立的证人：

| 证人 | 回答什么 | 可信度 |
|---|---|---|
| 测试 | 机器判过了没 | 高，但只覆盖有测试的部分 |
| git | 时间有没有把这份改动扔掉 | 高，最接近"真实接受" |
| 人 | 用户有没有再动手改 | 中，需时间窗与相似度收敛 |

### 6.2 三层信号（成本由低到高）

**第 0 层：会话文件里本来就有的证据（零成本）**

已在 magpie 的会话解析代码中确认存在的字段：

```
tool_use_id（28 处） / tool_result / is_error（7 处）
toolUseResult: { stdout, stderr, interrupted }
exit_code（50 处） / durationMs（43 处）
cwd / sessionId / timestamp
工具名：Bash（25 处）、exec_command（14 处）、Write（9 处）、Edit（8 处）、Shell（4 处）
model（570 处），calls.go:32 注释：「for Claude, the one the vendor answered」
```

最后一条很关键：**记录的是供应商真正回答的模型，不是别名**——归因天然可对齐。

**第 1 层：自己执行验收命令（需要托管进程）**

会话里的 `exit_code` 并非所有格式都可靠。真正硬的是 PHI 自己跑用户预置的验收命令，拿自己看到的退出码。这是 magpie 结构上拿不到的。

**第 2 层：仓库事实（最硬）**

- `git log --since` 看改动是否被 revert / reset
- 任务后 72h 内同一批文件是否被再次编辑
- 任务结束时文件是否真的变过（未变 = 空交付，最容易被漏掉的一类失败）

### 6.3 判定规则（把模糊变可算）

**任务单元切分**：`session_id × cwd × 空闲间隔`（>30 分钟切一刀），并提供"这其实是两个任务"的手动修正入口。

**三档状态，不给分数**：

| 状态 | 条件（按优先级） |
|---|---|
| 返工 | ① 改动被 revert/reset；② 验收命令由红转绿（说明第一版是错的）；③ 72h 内同一文件被再次编辑且 diff 相似度低于阈值 |
| 通过 | 验收命令绿，且 72h 内无上述返工证据 |
| 未证实 | 无验收命令、仓库非 git、或样本不足 —— **必须显式显示"未证实"，不许算成成功** |

**归因**：按文件算最近一次编辑者；一个任务动了 12 个文件、9 个是模型 A 写的，就按行数加权记给 A。多 agent 协作时归给"最后兜底的那个"。

**时间窗**：24h 太短（周末误判），7 天太长（掩盖问题）。默认 **72h**，并在界面上写明"这是 72 小时观察窗的结论"。

### 6.4 四个必须承认的陷阱

1. **人类二次编辑 ≠ 返工**。用"相似度 + 是否触及模型改过的那几行"收敛，而不是"碰过就算"。
2. **模型混用**。接棒场景下一个任务中途换了模型，必须记录"这一版是谁写的"，否则张冠李戴。
3. **测试缺失的项目**。大量仓库没有可跑的测试，只能落"未证实"，**不能用"没有报错"冒充通过**。
4. **样本量**。n<5 只显示"样本不足"，不显示百分比。

### 6.5 为什么不能一步到位：三个洞

**洞 ①：分母污染（最致命）**
若"通过率"的分母是"这个模型自己跑过的测试"，结论会完全反掉：越爱跑测试的模型，分母越大、通过率越低；从不跑测试的模型，分母为 0，永远 100%。要修，分母必须换成"同一批任务"——而"任务"这个刻度会话里没有。

**洞 ②：只有自述，没有独立裁决**
`is_error` 是 agent 自己工具调用的结果，它完全可以一条测试都没跑就宣布完成。高通过率可能只是"什么都没验证"。

**洞 ③：返工是时间的函数，不是快照的函数**
"72h 内有没有被再次修改"在任务刚结束时还没有答案。返工追踪必须**常驻观察**，是一条流水线，不是一次扫描。

### 6.6 补缺口的最小工程量

| 缺口 | 做法 | 量级 |
|---|---|---|
| 模型归因 | 会话 `model` → 真实供应商模型；用 PHI 网关日志交叉校准 | 小（数天） |
| 任务切分 | `session × cwd × 空闲间隔` + 手动修正通道 | 中（1–2 周） |
| 结果裁决 | 可选验收命令 + git 交叉 + 常驻回扫 | 大（真正的工程量） |

### 6.7 发布节奏（同时也是叙事节奏）

> **v0（立即可做）**：可靠性榜 —— 五个数，纯会话，立刻能出。
> **v1（1–2 周）**：加任务切分，指标改为"每任务"，分母终于对齐。
> **v2（1–2 个月）**：接上验收命令与 git，质量榜才敢叫"成绩单"。

**顺序不能反**：先让用户认可"它数得准"，再谈"它判得对"。第一版绝不做"按成绩单自动切模型"——只观测、不下命令。

### 6.8 样本覆盖偏差

PHI 只能读到它支持且明文落盘的会话格式。部分 agent 不落明文或需要授权，那么这部分模型进不了榜——**样本覆盖不全就会得出错误排序**。因此每个模型必须显示 n，n<5 只写"样本不足"。

## 七、v0 可靠性榜：今天就能算的五个指标

| 指标 | 数据来源 | 排除条件 |
|---|---|---|
| 工具调用失败率 | `is_error` / `tool_result` | 排除被中断（`interrupted`）的调用，单独统计 |
| 被中断率 | `interrupted` | 用户主动 ESC 无法区分，需在 UI 注明 |
| 空交付率 | 会话内无任何成功的 `Write`/`Edit` | 纯问答类任务需排除 |
| 单步失败与耗时 | `exit_code`、`durationMs` | 仅统计有该字段的格式，其他标记"不支持" |
| 单任务成本与上下文膨胀 | token / cache 字段 | 与任务切分联动，否则只到"每会话" |

**这一版的商业价值**：用户会相信"Kimi 在我这个项目上工具调用失败率是 GLM 的 2.3 倍"，因为那是他自己的记录，不是 benchmark。**但它必须被诚实地命名为"可靠性"，不能叫"能力"或"质量"。**

## 八、竞争风险

1. **速度风险（最高）**：目标仓库每天 100–290 次提交。今天是盲区，下周可能被补上。尤其"结果衡量"这件事，只要有人在它的 issues 里提，它一周内就能做出来。
2. **位置优势不等于永久优势**：它目前不碰工作区，是产品选择而非技术限制。若它愿意加一个"跑测试"的插件工具，"成绩单"的先发优势会被大幅削弱——但它要承担推荐责任，这与它当前的克制气质冲突。
3. **结论置信度**：本文关于 magpie 的判断基于**代码存在性、注释与设计文档**，未实际运行验证其在真实使用中的表现；PHI 侧能力来自其 README，未经源码核验。

## 九、建议的下一步

1. **先做 50 个任务的人工标注校准**：在真实仓库上跑，标注"完成/返工/未证实"，再与算法输出对齐，得出误判率。**这一步不能省**——否则产品会变成瞎指挥。

## 十、编排接力的落地方案：以 Backlog.md 为载体

> 定位：**节十是设计建议，不是已实现方案。** 其可行性依赖两个尚未核实的点，见 10.9 与附录 C。

### 10.1 为什么选它：几乎 1:1 对齐

Backlog.md（`MrLesk/Backlog.md`，MIT，npm 包名 `backlog.md`）是一个 **Markdown 原生**的任务管理器与看板可视化工具，面向 AI agent 设计，自我定位为：**"AI agents write the code. You review the tasks: before, during, and after."**

它的三个复查检查点与本文的接力设计高度重合：

| 本文设计（第 5 节） | Backlog.md 现成机制 | 判断 |
|---|---|---|
| Work Order 交接单 | 每张卡是一个 `.md` 文件，随仓库走 | **直接复用，省 1–2 周契约设计** |
| `goal` | 卡片 Description | 对齐 |
| `accept` 验收断言 | Acceptance criteria + Definition of Done | 概念对齐，**但它是给人读的文字** |
| `touched` / `forbidden` | 无 | PHI 需补 |
| `carry.leftovers` | Notes / 依赖关系（dependencies、milestones） | 部分对齐 |
| 三段流水线 | 三列：spec → plan → code | 几乎 1:1 |
| 门 1/2/3 | 三个 review checkpoint | 概念相同，**判决主体不同** |

关键差异一句话：**它的"复查"由人完成，PHI 的"复查"由命令与仓库完成。**

### 10.2 它解决什么，不解决什么

- **解决**：任务的结构化、拆分、依赖与里程碑、看板视图、跨会话的持久记忆（任务账本随 Git 走）、本地优先无服务端。
- **不解决**：① 执行验收命令并取退出码；② 判定改动是否越界；③ 校验复查者的证据是否真实；④ 会话与成本归因。

**后四项恰好是 PHI 的本职。** 因此不建议 PHI 自研一套看板，而应做它的**执行器 + 判决器**。

### 10.3 三层集成：从"看得见"到"会接力"

**L1｜只读（数天，可立刻发版）**
PHI 扫描仓库内 `backlog/` 目录下的任务文件，在自有界面呈现：这张卡正被哪个会话在做、已花多少 token、多久没有新动作。
- 输入：任务文件（Markdown + frontmatter/字段，**schema 待核实**）
- 输出：卡片 ↔ 会话的关联视图
- 价值：解决一个真实痛点——**卡挂在板上，人不知道 agent 到底在不在干**。

**L2｜回写（1–2 周）**
PHI 把门的判定结果写回卡片（通过其 CLI 或 MCP 接口，**具体子命令以当前版本文档为准**），使卡片成为唯一事实源。
- **禁止双份状态**：PHI 不得自造一份任务数据库，否则必然与卡片打架。
- 回写内容：门判定、证据摘要、耗时与成本、失败原因。

**L3｜驱动（真正的编排）**
PHI 以卡片为输入启动 agent（各 CLI 的非交互模式），过门后自动推进列，失败按 10.5 回退。到这一步才叫"接力"，前两步只叫"看得见"。

### 10.4 数据契约：卡片上必须补的四个字段

在不破坏原有格式的前提下，PHI 在卡片中追加一段机器可读块（示例为设计草案，非真实 schema）：

```yaml
phi:
  accept:                        # 门 2 的可执行断言，替代纯文字 AC
    - cmd: pnpm test -- auth
      expect: exit 0
    - cmd: pnpm build
      expect: exit 0
  touched:                       # 允许改动范围，越界即失败
    - src/auth/**
    - tests/auth/**
  forbidden:
    - package.json
    - src/billing/**
  role: implement                # plan | implement | review —— 决定该阶段权限
budget:
  max_tokens: 400000
  max_minutes: 40
```

**为什么要这一段**：Acceptance criteria 是给人读的，门 2 需要机器可判定的断言；`touched`/`forbidden` 是"并行写坏仓库"的唯一防线；`role` 决定谁只读、谁可写。

### 10.5 三道门的判定（伪代码）

```python
# 门 1：计划成立（人可读 + 机器可查）
pass1 = exists("PLAN.md") and has_accept_commands(card) and len(touched) > 0

# 门 2：实现成立（PHI 亲自执行，不采信 agent 自述）
for a in card.accept:
    rc, out = phi.exec_in_worktree(a.cmd, timeout=a.timeout)
    if rc != a.expect_exit: return FAIL(gate=2, evidence=out)
diff = phi.git_diff(base=run.base_commit)
if not subset(diff.files, card.touched): return FAIL(gate=2, evidence=diff.files)

# 门 3：复查成立（强制证据锚点）
for claim in review.claims:
    if not phi.verify_anchor(claim.file, claim.line, claim.quote):
        return INVALID(reason="复查意见缺少可校验证据")
return PASS if all(claim.ok for claim in review.claims) else FAIL(gate=3)
```

**门 3 是全案最花心思的一块**：复查模型天然倾向放行，强制它给出「文件＋行号＋原文引用」并由 PHI 校验真伪，能在它敷衍时当场抓住。**没有门 3，这套东西就是玩具。**

### 10.6 隔离、权限与回退

- **隔离**：每个 run 用独立 `git worktree`（或独立分支）；**不做并行写同一目录**。
- **权限**：`role=plan` 与 `role=review` 只读，`role=implement` 是唯一可写者。这一条消灭"复查顺手把代码改了"的经典事故。
- **回退阶梯**：门 2 失败 → 重试实现（≤2 次）→ 退回门 1 重做计划 → 仍失败 → 转人工，整 run 标记为"需要人"。
- **预算闸门**：超 token/时间上限即停并报告，绝不静默续跑。
- **分支卫生**：`backlog/` 的任务文件变更与功能 PR 分开提交，否则每张卡的 diff 都被任务文件污染。

### 10.7 MVP 与工期

> 只做两段、串行、人工放行：
> **Codex 实现 → 门 2 跑测试 → 人点"送复查" → Claude Code 只读复查（带证据锚点）**

| 工作项 | 量级 |
|---|---|
| L1 读卡片 + 关联会话 | 数天 |
| worktree 隔离 + 门 2 执行 | 数天 |
| L2 回写 + 卡片扩展字段 | 1–2 周 |
| 门 3 证据锚点校验 | 最花心思，1–2 周 |
| 明确不做 | 并行、动态分工、自动选模型、跨仓库 |

### 10.8 与「成绩单」合流（关键）

编排产生的每一条门判定，天然就是成绩单的一行数据：

```
Verdict(gate, pass/fail, model, tokens, cost, duration, evidence)
```

- **没有编排**：成绩单只能测"单个 agent 干活"。
- **有了编排**：它能测"**谁适合哪个角色**"——实现角色上一次过门率、复查角色上误判率。

这才是真正的壁垒：**别人可以抄"看板 + agent"，抄不了"你的仓库里积累了两百条角色级判定"。** 因此本文的建议顺序不变：**先成绩单 v1，再编排 L2/L3**。

### 10.9 五个坑

1. **别打破"一卡一上下文一 PR"**。它的价值就在 diff 小到人能读完；让一个 agent 连做五张卡，复查即刻失效。
2. **AC 必须升级为可执行断言**，否则门 2 永远只能靠人点。
3. **别把它的 Web UI 当主界面**。PHI 已有 GUI，把它当数据层，否则两套界面互相打脸。
4. **格式会演进**（当前 README 标注 v1.40），解析层要做适配，不要写死。
5. **npm 依赖是外部风险**：PHI 应能在不装它的前提下**只读卡片文件**，CLI/MCP 仅用于回写。

### 10.10 一个顺手的战略动作

把 `accept` 扩展成可执行断言这件事，**建议上游贡献给 Backlog.md**：它要"可验证"，PHI 要"可执行"，利益一致。贡献一个 schema 提案比打一场竞品战争便宜得多。

### 10.11 备选与边界

- `antopolskiy/kanban-md`：同为 Markdown 原生、更轻，若只要板子不要流程可考虑。
- 面向"多 agent 并行容器隔离"的工具属另一条路线，本文未核实其现状，**不作为依据**。

## 十一、教训库（Failure Museum）：最小代价的入场理由

> 本节同属设计建议。其中 token 与金额均为**量级粗估**，非报价；可行性依赖一项未核实的前提，见 11.9。

### 11.1 是什么

把失败会话自动沉淀成**仓库级的"禁区清单"**，并回喂给每一个 agent：

```
[2026-10-08] src/billing/**：直接改 schema → 11 个测试红。
证据：pnpm test -- billing 退出码 1；2 小时内同批文件被人工重写。
下次：先跑 migration 校验，再动 schema。
```

一句话价值：**magpie 记得你做过什么，PHI 记得你是怎么炸的。**

### 11.2 为什么是它，而不是更炫的东西

用第五节那四条标尺量：

| 判据 | 教训库 | 说明 |
|---|---|---|
| 只有执行现场能得出 | 部分成立 | 失败会话与 git 事实确实是额外资产 |
| 用户一句话就懂 | ✅ | "它记得我上次怎么炸的" |
| 数据随时间增值 | ✅✅ | 教训越积越准，换工具就清零 |
| 对手要做必须改定位 | ⚠️ | magpie 有 `memory`，但它的记忆不承认"任务会失败" |

对照 magpie：`internal/memory` + `memdistill`（每晚 "Dreaming" 整理）做的是**正向记忆**——"我们做过什么、约定是什么"；本节做的是**负向记忆**——"哪里不能碰"。两者同构但不同向，**负向记忆的边际价值更高，因为失败比成功更贵**。

### 11.3 四段流水线与成本分布

成本分布极不均匀，这是本节最该记住的一张表：

| 阶段 | 做什么 | 要不要模型 | 成本量级 |
|---|---|---|---|
| ① 采集 | 解析会话（工具调用、退出码、改动文件）＋ 读 git | **不要** | 0 |
| ② 判定 | 这条算不算一条"失败教训"（阈值规则） | **不要** | 0 |
| ③ 提炼 | 把结构化事件写成一句人话 | **可选** | 每晚几分钱 |
| ④ 注入 | 把教训塞进 agent 上下文 | **不要模型，但吃 token** | **主成本** |

### 11.4 第③段可以完全不调模型

用固定模板生成，上面 11.1 那条例子就是模板输出。

**模板的好处不只是省钱，更是稳定**：模型每次改写措辞，注入内容就天天变，而"天天变"正好撞上 11.6 的缓存问题。模型只在"合并同类教训"这种低频动作上出场。

### 11.5 第④段：三个阀门

**阀 1｜按命中注入，不做全量倾倒**
教训带路径标签（`src/billing/**`）。当前任务碰到该路径才注入那一条——**匹配用字符串前缀，零 token**。一个仓库攒到 200 条，单次会话可能只注入 2 条。

**阀 2｜给注入设字符预算**
例如全局 500 字 + 项目 300 字，超了就只留 top-k（按"命中次数 × 最近性"排序）。这一做法有先例可参：magpie 的 `internal/memory` 就是按 global/project 各自的**字符预算**管理的（源码注释明确写了 budgets），说明这是该层的通用工程共识。

**阀 3｜只注一次，不注每轮**
注入点放在会话起始（或 `AGENTS.md` 这类常驻文件），不要在长会话里反复追加。

### 11.6 真正被忽略的成本：它会打穿 prompt cache

这一条比 token 单价重要得多。

- prompt cache 命中依赖**前缀稳定**。教训清单若每次会话都变（新增一条、重排顺序、模型换个措辞），缓存就命中不了；
- 未命中时的输入价格往往是命中时的数倍（倍率因供应商而异）；
- 省下的"几分钱提炼费"，可能在上百次会话中被放大成真正的成本。

**设计上的直接推论：**

1. **日更，不会话更**——每天固定时间重算，白天不变；
2. **追加，不重排**——新教训挂在末尾，老的顺序不动；
3. **版本号写进文件头**（如 `lessons v37`），让 PHI 与缓存策略对齐；
4. 顺带解释一个从 magpie 源码里看到的设计：它的 `tune` 包专门算"Claude Code 的 cache 保留多久最省"，说明**上下文稳定性本身就是一门成本学问**。

### 11.7 量级估算（粗略，非账单）

假设：每条教训约 120 字，单次会话注入 3 条 ≈ 360 字 ≈ 500 token；每天 20 个会话。

- 注入成本 ≈ **1 万 token/天**（约 30 万 token/月）
- 按常见输入价区间折算，大致是**每月几元到几十元人民币**的量级（**粗估，具体取决于供应商计价与缓存命中率**）

反过来，如果没有阀 1 与阀 2（每晚重写全部教训、每次全量注入），很容易变成每月几百万 token——用户一定会关掉它。**教训库能不能活，取决于注入的克制程度，而不是模型多聪明。**

### 11.8 最大风险：不是钱，是错注入

一条错误的教训会让 agent 绕开正确做法（负迁移），比不注入更糟。因此：

- 每条教训必须支持**一键删除**，且删除理由回写（防止下次重算又长出来）；
- 每条教训统计**命中后相关任务的一次通过率是升是降**——**用成绩单反验教训库本身**。
- 教训库与成绩单互为验证：成绩单判"谁干得好"，教训库影响"下次怎么干"，两者闭环才算系统。

### 11.9 MVP 与一个未核实前提

**MVP（零模型调用版）**：模板生成 + 路径命中 + 字符预算 + 日更。只依赖两样东西：会话解析（PHI 已有）与一次注入通道。

**未核实前提**：PHI 是否具备把教训注入 agent 上下文的能力（写 `AGENTS.md`、写成 Skill、或首轮注入），目前只能从其 README"统一管理 MCP、Skills 与提示词"**推断**，**未经核验**。这一点若不成立，整个功能不成立——应作为动手前第一个验证项。

**2026-11-12 补充**：已在 PHI 仓库源码中核对，注入通道成立（见 13.1）。

| 工作项 | 量级 |
|---|---|
| 会话 → 失败事件提取（与成绩单共用） | 数天 |
| 模板生成 + 路径标签 + 预算 | 数天 |
| 注入通道 + 日更/版本号 | 数天～1 周 |
| 命中率与效果统计（接成绩单） | 1 周 |

### 11.10 与另外三个功能的关系

```
教训库 ──提供“任务-结果”结构化记录──▶ 成绩单
   │                                        │
   └──反验教训质量───────────┘
                        成绩单 ──角色级判定──▶ 编排接力
```

- **教训库是地基**：它跑起来，成绩单所需的结构化记录顺手就有了；
- **成绩单是护城河**：它跑三个月，用户就走不了；
- **编排接力是放大器**：它让"谁适合哪个角色"成为可测的事实；
- **接棒是钩子**：它解决问题的痛感最强，适合做发布会的那个 demo。

因此建议的落地顺序为：**教训库（1 个月，轻）→ 成绩单 v0 → 信任闸 / 接棒 → 编排接力 → 私有评测集**。
注意：本节不改变第八、九节的结论——成绩单仍是护城河与主叙事，只是**入场顺序前移了一个更小的东西**。

## 十二、候诊室（Human Queue）

> 本节为设计建议，未经实现与实测。其核心前提（能否可靠识别“进程正停在等人输入”）**未核实**，见 12.9。

### 12.1 痛点：不是看不完，是不知道谁在等你

重度用户的一天不是这样过的：

```
跑一个任务 → 等 → 看结果 → 再跑
```

而是这样过的：

```
开 3 个终端、4 个 agent、6 个任务 →
其中一个在等权限确认，一个在等“选 A 还是 B”，
一个已经失败但你没看见，剩下三个在正常干活 →
你挨个标签页去看 → 回到第一个时它已经等了四分钟
```

这个痛点一天发生**几十次**。它不值得写进 roadmap 发布会，但它是真实吞掉注意力的地方。

### 12.2 是什么：把所有“等我”收敛成一条队列

```
等你处理（3）
├─ feat/auth · Codex        要执行 pnpm add jsonwebtoken，等你允许（已等 4 分钟）
├─ api/refund · Claude      问你“退款接口走 v1 还是 v2”，[ A ] [ B ]
└─ tools/scrape · Gemini    失败，退出码 1，已生成交接单 [ 重试 ] [ 发复查 ]
```

三个特征，缺一不可：

1. **只收“卡在等人”**，不收“正在干活”——正常进度不进队列；
2. **带上下文**（哪个项目、哪个 agent、等了多久、在等什么）；
3. **带可执行动作**（允许/拒绝、选 A/B、重试、转发），而不是只给一条链接让人去翻。

### 12.3 怎么知道“卡住了”：三层信号，从硬到软

| 信号 | 可靠性 | 说明 |
|---|---|---|
| 进程阻塞在读 stdin（PTY 无输出且未退出） | 高 | 需终端托管；这是 PHI 独有的观测点 |
| 进程已退出且退出码非 0 | 高 | 当前会话已结束，带输出尾部作为证据 |
| 会话活跃度跌零、且最后一步是写文件或跑命令 | 中 | 启发式：可能已完成但未声明，也可能卡住 |
| 日志文本命中固定模式（y/n、Choose、permission） | 中 | 仅作辅助，不可单凭文本判定 |

**原则：宁可漏报，不可误报。** 误报一次，用户就会关掉它；漏报一次，他只是再点一轮标签页。

### 12.4 与“通知中心”的区别

大多数工具做了通知中心，然后变成又一个红点焦虑源。差异在三处：

| | 通知中心 | 候诊室 |
|---|---|---|
| 边界 | 什么都收 | **只收“等我”** |
| 空态 | 总有东西 | **应该是空的**——空是对的，不是失败 |
| 出口 | 点击跳转 | **就地决策**，不跳页 |

第三条是关键：跳页就等于把“上下文重建”的成本又还给了用户。

### 12.5 去重与节流

- 同一 agent 反复追问同一个问题的，**合并成一条**（记次数，不刷屏）；
- 同一时刻最多推 N 条（建议 3），其余折叠为“还有 2 条”；
- 用户正在看的那个终端，其条目**不重复展示**（避免“我在看它还在叫我”）；
- 等待超过阀值（如 5 分钟）且用户不在电脑前，才考虑系统级提醒——否则一律静默。

### 12.6 为什么对手做不了

magpie 看的是 **HTTP 请求**。它能看到“模型说了什么”，看不到“你的 agent 进程正停在等待输入那一行”。
要做这件事，必须同时拥有：**进程（PTY）+ 会话（判断任务边界）+ 多任务并发视图**。而 magpie 的产品形态是菜单栏 + 网关，它刻意不碰终端。

### 12.7 三个真实风险

1. **红点焦虑**：如果队列经常非空，它就失败了。必须把“为空”当成设计目标。
2. **误判成本**：把“思考中”当成“卡住”而弹窗，会打断正在干活的 agent——所以进程阻塞信号优先于启发式。
3. **隐私**：队列里含任务名与命令内容，默认只存本地、不上传，与第十一节同一原则。

### 12.8 MVP 与工期

**MVP（一周量级）**：只做两个信号——进程阻塞读 stdin + 退出码非 0；只做一个界面——一条队列；只做三个动作——允许/拒绝、重试、跳转对应终端。

| 工作项 | 量级 |
|---|---|
| 终端状态监听（忙/阻塞/退出） | 数天 |
| 任务边界与去重合并 | 数天 |
| 队列 UI 与就地动作 | 数天～1 周 |
| 空态与节流策略 | 数天（容易被少算，但它决定生死） |

### 12.9 一个未核实前提

整个功能成立的前提是：**PHI 能区分“进程正在干活”与“进程停在等待输入”**。
这需要 PTY 层面的可观测能力（或各 agent 的非交互模式提供状态信号）。本文未能核实 PHI 的实现，**动手前应作为第一个验证项**——建议先用一个最简单的实验：起一个会要求 y/n 确认的命令，看 PHI 能否在不解析文本的前提下分辨“正在跑”与“在等我”。

**2026-11-12 补充**：PTY 托管已核对成立，但“在等我”仍差一个探针（见 13.1）。该探针已单列为 G0，是本文建议的第一个动手项。

## 十三、源码核对后的三处修订（2026-11-12）

> 本节是前十二节写完之后的一次回头核对。核对对象是 PHI 自己的仓库（本地工作副本，HEAD `8a8381e`）。13.1 的结论是代码存在性事实；13.2–13.4 仍是设计判断，未经实现与实测。

### 13.1 两条“未核实前提”已经可判：一真、一半

| 原附录 C 项 | 核对依据 | 结论 |
|---|---|---|
| 第 7 项：PHI 能否把教训注入 agent 上下文 | `src-tauri/src/services/prompt.rs`（`AGENTS.md` 的读写、外部改动检测与回滚）、`src-tauri/src/services/skill.rs`（`SKILL.md` 的 SSOT 与按 app 同步） | **成立**。教训库不必自建注入通道，接 `AGENTS.md` 既有通道即可 |
| 第 9 项：PHI 能否分辨“在干活”与“在等我” | `src-tauri/build.rs` 静态链接 `libghostty.a`；`src-tauri/src/terminal/native.rs`（macOS 原生）已有 `exited` 事件与 `phase` / `generation` 状态机 | **一半成立**。PTY 是自己的、进程退出可判；“停在读 stdin”仍缺一个探针 |

这条核对的意义超过补两行附录：**第八节担心的“位置优势被抹平”，实际要求对方改变产品形态。** magpie 是菜单栏 + 网关，要有 PTY、要有仓库里 `AGENTS.md` 的写权，就得先变成工作台。位置比原文估计的更硬。

但缺口仍在前置位置上：

**G0（半天量级的实验）**：在真实 agent 会话里起一个要求 y/n 确认的命令，观察 PHI 能否在不解析终端文本的前提下判定“停在等输入”。判定标准建议写死：延迟 < 2s、误报 0。G0 不过，第十二节的候诊室退回普通通知中心，第六节的“第 1 层验收”也只能靠会话里自带的 `exit_code`。

### 13.2 一处内部矛盾：教训库与成绩单互相等待

第十一节说教训库靠成绩单反验（11.8：“看命中后相关任务的一次通过率是升是降”），第六节说成绩单要 72 小时观察窗才有答案（6.5 洞③）。两条并列，就成了：教训库等成绩单 v2，成绩单 v2 等三个月。

**修法：给教训库配一个不依赖成绩单的反验指标。** 只用 git 与验收命令：

```
命中组 = 教训生效后、触碰同一路径的下一个任务
指标 A：命中组验收命令全绿的比例
指标 B：命中组 72h 内同批文件被重写的比例
对照  ：同仓库、同模型、未命中该路径的任务
```

指标 A / B 只依赖两样东西——验收命令的退出码、git 的再次编辑记录——不需要任务切分，不需要模型归因，也不需要成绩单。代价是样本少、噪声大，因此它只能回答“这条教训像是有用的还是像是有害的”，回答不了“提升了几个点”。**但这已经够用来支撑一键删除的决定，也就够了。**

### 13.3 报告漏掉的一整块：第 0 天

“数据随时间增值”是本文给教训库与成绩单的高分理由，但这句话的反面一直没写：**第 0 天它们都是空的**。

| 功能 | 第 0 天 | 第一份价值何时出现 |
|---|---|---|
| 成绩单 | n=0，只能显示“样本不足” | 数周～三个月 |
| 教训库 | 禁区清单为空 | 攒到若干次真实失败之后 |
| 候诊室 | **开箱即用** | 第一次有 agent 停下来等人 |

这里需要与一页结论第 9 条对齐：教训库“当天可被感知”指的是**装上当天它就开始记录、并且能看见第一条禁区**，不是当天就有统计意义的效果。两者不矛盾：入场快与有效果慢，本来就是两件事。

按这把尺子重排，入场顺序要改：

```
G0 探针（半天）→ 候诊室（第 0 天就有感知）→ 教训库 → 成绩单 v0/v1 → 接棒 → 编排接力
```

这不是推翻第十一节，而是把它的两个理由分开：**“让人愿意住进来”该由立刻可见的东西承担，“让人搬不走”才是成绩单的活。** 候诊室只解决前者，且第一天就能被感知；教训库解决“记得你是怎么炸的”，价值更高，但必须等时间。

风险要一并写清：候诊室是四个功能里**最容易长成红点焦虑**的一个，12.7 的三条风险因此从“注意项”升级为“发布门禁”——队列经常非空，就砍掉它，而不是把它调小。

### 13.4 没人算过的一笔账：界面预算

四个功能 = 四个新界面（一条队列、一张成绩单、一份禁区清单、一块看板）。工作台的界面预算比功能预算更紧：每多一个常驻面板，就多一份“这软件越来越重”的抱怨。

建议压到两处：

- **候诊室**做成状态条的另一种形态，不新增屏；空态即默认态（空态是设计目标，不是异常）；
- **成绩单与教训库**并入同一页——一个看结果、一个看原因，天然是同一页的两栏，分开放反而要用户自己连线。

### 13.5 本节没有改变什么

- 成绩单仍是护城河与主叙事（第五节、第十节、11.10 的结论不变）；
- 编排接力仍是“最好的融资故事、最不该现在做的东西”；
- 所有判定规则、估工与成本仍是设计口径，**未经实现与实测**。本节新增的唯一“事实”，是 13.1 那两条代码存在性结论。

## 附录 A：术语与指标词典

| 术语 | 含义 | 易混点 |
|---|---|---|
| PTY | 伪终端，进程与终端之间的接口 | 与"会话文件"不是一回事：PTY 是实时的，会话文件是落盘的 |
| 会话（session） | agent 一次对话的记录，落为 jsonl / db | 不等于"任务"：一个会话可含多个任务 |
| 任务（task） | 本次分析引入的刻度，由 `session × cwd × 空闲间隔` 切分 | 不是 magpie 的概念，它没有这个对象 |
| 一次通过率 | 首次验收即通过的任务占比 | 分母必须是"同一批任务"，不能是"各模型自己跑过的测试" |
| 返工率 | 72h 内被 revert / 被重写 / 由红转绿的任务占比 | 人类二次编辑不必然等于返工 |
| 空交付率 | 会话结束时未产生任何成功写入的占比 | 纯问答类任务需排除 |
| 未证实 | 缺少验收命令、非 git 仓库或样本不足 | **不得计入成功** |
